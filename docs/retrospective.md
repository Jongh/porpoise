## 2. 세 번의 정체성

porpoise는 한 번도 같은 것이었던 적이 없다. 이 변화 자체가 이 프로젝트의 가장 큰 산출물이다.

1. **워커 (v0.1 ~ v0.18) — "LLM에게 단계별로 시킨다"**
   `Planning → Development → Testing → Review` 4단계를 각각 LLM 호출로 실행하고 JSON 세션으로
   이어 붙였다. 에이전트가 약하다는 전제 아래 사람이 하던 개발 절차를 프롬프트로 쪼개 흉내 낸 구조였다.
2. **지휘자 (v0.19 ~ v0.26) — "에이전트에게 통째로 맡기고, 검증은 독립적으로"**
   코딩 에이전트가 스스로 계획·구현·테스트를 해낼 만큼 강해지자, 단계 분할은 오히려 방해가 됐다.
   `Brief → Dispatch(격리 worktree) → Verify(독립 검증자) → Integrate`로 피벗(M20)하고,
   M22에서 기본값으로 승격했다. 병렬 함대·의존성 DAG·감사 기록·비용/예산이 이 시기에 붙었다.
3. **관제탑 (v0.27 ~ v0.37) — "사람은 대시보드에서 게이트만 누른다"**
   웹 대시보드(관측 → 라이브 SSE → 게이트 제어 → 런처), halt 회복(파킹·재계획), 비용 라우팅까지.
   터미널 없이 함대를 운영하는 데까지 갔다.

**핵심 교훈**: 모델이 강해질수록 오케스트레이터의 가치는 "어떻게 코딩할지 지시"에서
"무엇을 할지 정하고, 했다는 주장을 믿을지 판정"으로 이동한다. porpoise는 그 이동을 직접 겪으며 증명했다.

## 3. porpoise가 남긴 것 (의미)

- **거버넌스는 외부 루프다.** 코딩(내부 루프)은 에이전트에게, 마일스톤 계획·DoD·독립 검증·감사·
  릴리즈(외부 루프)는 별도의 규율로. 이 분리가 porpoise의 최종 철학이었고 tide의 출발점이 됐다.
- **"만든 자가 아닌 자가 통과를 판정한다."** 독립 검증자는 conductor 신뢰의 핵심이었다. 검증자 파싱
  실패·false-negative(M21), 폴백 정책(M22) 등 신뢰를 실제로 얻는 데 드는 비용도 함께 배웠다.
- **부수효과의 격리.** worktree 격리, 커밋은 통합 단계에서만 — "어떤 단계가 무엇을 바꿀 수 있는가"를
  구조로 강제하는 습관.
- **라이브 검증은 단위 테스트로 대체되지 않는다.** M26·M27·M29의 버그 수정(변경 감지·report stale·
  untracked 충돌·fresh 체크아웃)은 실 실행에서만 드러났다. 매 사이클 "운영자 라이브" 항목이 남은 것은
  이 도구의 한계이자 정직한 기록이다.
- **방법론이 도구보다 오래 산다.** porpoise를 만들던 *방식* — 마일스톤 → 구현 → 리뷰 → 릴리즈,
  보고서로 남기는 판정, 후속 항목 추적과 회고 — 은 Rust 바이너리 없이도 성립했다. 그것이 tide다.

## 4. 왜 끝내는가

- **실행 엔진이 범용 에이전트 쪽으로 흡수됐다.** Claude Code 자체가 서브에이전트·병렬 실행·훅·
  플러그인을 갖추면서, porpoise가 직접 구현하던 dispatch/worktree/병렬 함대는 플랫폼 기능 위의
  얇은 규율로 표현할 수 있게 됐다. 2만 줄의 Rust가 지키던 것을 슬래시 커맨드와 훅이 지킨다.
- **다음 방향이 비었다.** v0.37.0 시점 retro가 기록했듯 두 뿌리 문제(halt·비용)가 해소된 뒤 남은 것은
  점진적 고도화뿐이었다.
- **실제로 쓰인 것은 방법론이었다.** M37부터 porpoise 자신이 tide 체계(`docs/milestones`·`docs/reports`)로
  개발됐다 — 도구가 자기 후계자의 첫 사용자가 된 셈이다.

## 5. tide로 이전된 아이디어

| porpoise | tide |
|----------|------|
| 마일스톤 단위 사이클 (Planning→Development→Testing→Review, `.porpoise/milestones/M{n}.md`) | `/tide:milestone → /tide:impl → /tide:review → /tide:release`, `docs/milestones/M{N}.md` |
| Review 세션의 NEXT/PREV 판정 · 독립 검증자 | `/tide:review` — 반증 시도 후 릴리즈 판정 (차단 등급은 `불가` + impl 반환) |
| 단계별 JSON 세션 · 감사 기록 | 단계별 보고서 `docs/reports/M{N}-impl.md`·`-review.md` |
| 커밋은 통합 단계에서만 · worktree 격리 | 부수효과 분리 — git 작업은 `release`에서만, tide-guard hook으로 기계적 강제 |
| `(deps:)` 의존성 DAG · 병렬 함대(`max_parallel`) | `/tide:cycle` — deps 기반 서브에이전트 병렬/순차 실행 |
| 멀티 프로젝트 대시보드 · 함대 관제 | `/tide:fleet`·`/tide:fleet-cycle`·`/tide:fleet-verify` (멀티 레포) |
| `porpoise status` | `/tide:status` |
| 게이트 승인 (gate 모드) | `release` 직전 정지 · 프리플라이트 |
| 실행 리포트 · 후속 항목 추적 | `/tide:retro` — 누적 회고·이월 원장 |

이전되지 **않은** 것: 다중 LLM 어댑터(`anthropic_api`·`openai_compatible`), 웹 대시보드·런처,
비용 계측/예산/모델 라우팅, 설치 패키지(msi/deb/rpm). 이들은 porpoise 저장소에 기록으로 남는다.

## 6. 맺음

porpoise는 "AI가 개발 절차를 대신 수행하는 도구"로 시작해 "AI 개발에 규율을 씌우는 방법론"으로 끝났다.
도구는 여기서 멈추지만, 그 방법론은 [tide](https://github.com/Jongh/tide)에서 계속된다.
