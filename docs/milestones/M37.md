# M37 — 런처: 대시보드에서 함대 실행·halt 재투입·설정 편집

## 목표

대시보드가 **관측·게이트 제어**를 넘어 **실행 자체를 시작·관리하는 통제실**이 된다. 운영자는
터미널에서 `porpoise`를 직접 띄우지 않고, 브라우저의 **[함대 실행]** 버튼으로 conductor 런을
기동하고, max_redispatch 소진으로 **halt된 task를 한 번에 재투입**하며, `[conductor]` 핵심
설정(병렬도·재투입 한도·승인 모드·모델)을 **대시보드에서 직접 편집**한다. 이로써 "관측 →
계획/게이트 제어 → 실행 시작"의 무터미널 사이클이 완결된다.

## 배경

M33 범위 제외 메모에 명시된 후속이다 — *"halt task 재투입 버튼·conductor 실행 시작 → 런처
(conductor 프로세스 수명 소유 필요)"*. M34~M36(M36.md `followups`)까지 매 사이클 우선순위에
밀려 이월돼 온 마지막 큰 조각이다.

지금까지의 통신은 **파일 매개·프로세스 무결합**이었다(M31 관측 live.json, M33 control/ 게이트).
M35에서 conductor가 대시보드를 **내장 기동**(`serve_in_background`, 포트 충돌 시 공존)했다.
런처는 그 방향을 **역전**한다 — **독립 실행 중인 대시보드가 conductor 프로세스를 spawn**한다.
이것이 M33 이후 계속 이월된 핵심 사유다: 대시보드가 **자식 프로세스의 수명을 소유**해야 한다.

세 축의 현 상태와 갭:
- **함대 실행**: 현재 런 시작은 터미널에서 `porpoise` 실행뿐. 대시보드에 spawn 진입점이 없다.
  (M35 내장 기동과 공존 — spawn된 conductor가 gate 모드면 자기 대시보드를 또 띄우려다
  `PortInUse`로 기존 대시보드와 공존: M35-T01에서 이미 처리된 경로를 재사용한다.)
- **halt 재투입**: `max_redispatch` 소진 시 task는 `live::set_task(..,"halted",..)` + halt 힌트
  파일(`{id}-conductor-halt.md`)로 남고, 현재 구제책은 *수동 작업 또는 max_redispatch 상향
  후 재실행*뿐(`src/conductor/mod.rs:279,508`). 대시보드 한 번 클릭으로 재투입할 길이 없다.
- **설정 편집**: M33은 제어 쓰기를 `.porpoise/control/`로 **한정**하고 *"코드·project.md·설정은
  일절 쓰지 않는다"*고 못 박았다. 런처는 이 경계를 **의도적으로 확장**해 `[conductor]` 설정의
  **화이트리스트 키**에 한해 쓰기를 허용한다(임의 TOML 주입 차단·필드별 검증).

설계 불변: 실행 백엔드를 제외한 통신은 여전히 파일 매개를 유지한다. spawn은 detached로 하여
대시보드 재시작이 진행 중 런을 죽이지 않게 한다. 모든 신규 쓰기 엔드포인트는 M32 허용 목록·
프로젝트 스코프 + M33 Origin 검증(CSRF 차단)을 상속한다.

## 태스크 상세

### M37-T01: 실행 백엔드 — conductor 프로세스 기동

**변경 파일**: `src/dashboard/launch.rs`(신규), `src/dashboard/mod.rs`(POST 라우팅)

- `POST /api/launch` (+`?project=<id>` — M32 `resolve`로 스코프). body 선택: `{yes?: bool}`
  (`--yes` 자동 승인 전달용, 기본 false → gate 모드 승인 대기).
- 검증: M33 `origin_allowed`(403)·등록 프로젝트만(404) 상속.
- **런 락**으로 이중 기동 방지: `.porpoise/run.lock`(또는 live.json의 RUNNING 상태) 존재 시
  409 "이미 실행 중". 락 파일에 spawn한 자식 PID·시작 시각을 기록. 정상 종료/비정상 종료 후
  stale 락 판단은 보수적으로(PID 생존 확인 불가 플랫폼 차 — 우선 live.json 종료 이벤트 기준,
  불확실하면 "강제 실행" 옵션은 후속으로 미룸).
- spawn: 현재 실행 파일 경로(`std::env::current_exe`)로 `porpoise`를 **프로젝트 디렉터리에서**
  `Command::new(exe).current_dir(project)` 로 기동. **detached**(stdin null,
  stdout/stderr는 `.porpoise/launch.log`로 리다이렉트)하여 대시보드 프로세스와 수명 분리 —
  대시보드를 닫아도 런은 계속된다.
  - 플랫폼 detach: Windows는 `CREATE_NO_WINDOW`/새 프로세스 그룹, Unix는 `setsid` 상당.
    플랫폼 분기는 `launch.rs` 내 작은 헬퍼로 격리하고 단위 테스트 대상에서 제외(통합 하니스로).
- 응답: `{ok:true, pid, log:".porpoise/launch.log"}` 또는 409/404/403.
- **M35 공존**: spawn된 conductor가 gate 모드라 자기 대시보드를 `serve_in_background`로 띄우려다
  `PortInUse` → 기존(런처) 대시보드와 공존(M35-T01 경로). 새 코드 불필요 — 회귀만 확인.
- 단위 테스트(순수 분리): 락 존재 시 409 분기, 미등록 프로젝트 404, Origin 403, 락 파일
  쓰기/파싱(PID·시각). 실제 spawn은 T05 하니스.

### M37-T02: halt task 재투입 (deps: M37-T01)

**변경 파일**: `src/dashboard/control.rs`(decision 확장), `src/conductor/{mod,gate}.rs`(오버라이드 소비)

- 제어 채널 재사용: `handle_control`의 `decision` 허용값에 `"redispatch"` 추가
  (approve|stop|redispatch). `redispatch`는 `gate_id`에 **task id**를 받아
  `.porpoise/control/redispatch-<task_id>.json`에 `{extra_budget: u32}` (기본 +1) 기록.
  gate_id 형식 검증(영숫자·하이픈)·Origin·스코프는 기존 그대로.
- conductor 런 진입 시(resume 포함) 각 task 처리 직전 `redispatch-<id>.json`을 확인:
  존재하면 **소비(삭제)** 후 해당 task의 halt 상태를 해제하고 `max_redispatch`에 `extra_budget`
  만큼 추가 예산을 부여한다(`integrate::decide`에 들어가는 유효 한도 상향). halt 힌트
  파일(`{id}-conductor-halt.md`)도 정리.
  - 핵심 흐름: **재투입은 다음 런에서 효력** — halt는 이미 끝난(또는 진행 중 다른 task로 넘어간)
    상태이므로, T01의 [함대 실행]으로 resume 런을 띄우면 오버라이드가 적용된 채 그 task가
    다시 시도된다. (실행 중 함대로의 핫-재큐는 스케줄러 복잡도가 커 본 마일스톤 범위 밖.)
- 소진/오버라이드 적용 로직은 순수 함수로 분리 + 단위 테스트(오버라이드 파싱·예산 합산·소비
  후 삭제·halt 힌트 정리·오버라이드 없으면 기존 동작 무변경).

### M37-T03: 설정 편집 백엔드

**변경 파일**: `src/dashboard/config_edit.rs`(신규), `src/dashboard/mod.rs`(라우팅), `src/config/workspace.rs`(검증 헬퍼 노출)

- `GET /api/config?project=<id>` → 현재 `[conductor]` 편집 가능 설정을 JSON으로(읽기):
  `mode`·`approval_mode`·`max_parallel`·`max_redispatch`·`serve_dashboard`·`dispatch_model`·
  `verifier_model`·`verdict_fallback`(노출 키는 화이트리스트로 고정).
- `POST /api/config?project=<id>` body: 위 키의 부분 집합. **화이트리스트 외 키 거부**,
  필드별 검증(예: `max_parallel`·`max_redispatch`는 양의 정수 상한, `approval_mode` ∈
  {console,gate}, `mode` ∈ {legacy,conductor}, `verdict_fallback` ∈ {pass,halt}). Origin·스코프 상속.
- 쓰기: 대상은 프로젝트의 `workspace.toml`(없으면 생성 위치 규약 따름). **임의 TOML 주입 방지**를
  위해 파싱→해당 키만 갱신→재직렬화(`toml` 크레이트)로 쓰되, 다른 섹션·값은 보존. 쓰기는
  `utils::fs::write_file`(루트 경계 검사) 경유. 검증 실패 시 400, 어떤 키도 쓰지 않음(원자성).
- **경계 확장 명시**: 이 엔드포인트만 설정 파일에 쓰기를 허용 — control/ 한정 원칙의
  의도적 확장(코드·project.md는 여전히 불가). 주석·문서에 사유 기록.
- 단위 테스트: 화이트리스트 외 키 거부, 필드 검증(범위·열거), 부분 갱신 시 타 섹션 보존,
  검증 실패 시 무쓰기.

### M37-T04: 런처 UI (deps: M37-T01, M37-T02, M37-T03)

**변경 파일**: `src/dashboard/static/{index.html,app.js,style.css}`

- **[함대 실행]** 버튼: 런 비활성(live RUNNING 아님) 시 노출 → `POST /api/launch` → 성공 시
  로그/라이브로 전환, 409면 "이미 실행 중" 안내. 진행 중엔 숨김(M33 정지 버튼과 공존).
- **halt 재투입**: 리포트/라이브에서 `halted` 상태 task 행에 **[재투입]** 버튼 →
  `POST /api/control {decision:"redispatch", gate_id:<task_id>}` → 성공 시 "다음 실행에서
  재시도" 토스트 + (런 비활성이면) [함대 실행] 유도.
- **설정 편집 폼**: 설정 패널에서 `GET /api/config` 로드 → 폼(숫자·셀렉트) → 저장 시

- 게이트/런 없을 때 시각 회귀 없음. 신규 버튼은 권한·상태에 따라 조건부 노출.

## 완료 기준

1. `cargo build` 경고 0개, `cargo clippy` 신규 경고 0개, `cargo test` 전체 통과.
2. 독립 실행 중인 대시보드의 **[함대 실행]** 버튼 한 번으로 conductor 런이 detached 기동되고
   (대시보드를 닫아도 런 지속), 이미 실행 중이면 409로 이중 기동이 차단된다.
3. spawn된 gate 모드 conductor가 기존(런처) 대시보드와 `PortInUse` 공존(M35 경로 회귀 없음).
4. `max_redispatch` 소진으로 **halt된 task**에 대시보드 [재투입] → 다음 [함대 실행] 런에서
   예산이 상향된 채 그 task가 재시도되고, 재투입 오버라이드 파일은 소비(삭제)·halt 힌트 정리된다.
5. **설정 편집**: `GET /api/config`로 현재 `[conductor]` 값을 읽고, `POST /api/config`로
   화이트리스트 키를 검증·저장하며, 화이트리스트 외 키·검증 실패는 거부하고 파일을 쓰지 않으며,
   갱신 시 `workspace.toml`의 다른 섹션·값은 보존된다.
6. 신규 쓰기 엔드포인트(`/api/launch`·`/api/config`·`redispatch` control) 모두 Origin 검증(403)·
   프로젝트 스코프(404)를 상속하고, 설정 쓰기는 `[conductor]` 화이트리스트로 한정(임의 TOML 주입 불가).
7. 게이트·런이 없을 때 대시보드 시각 회귀 없음, 표시 텍스트 XSS 방어(esc).
8. 단위 테스트(런 락 분기·재투입 오버라이드 소비·설정 검증/부분 갱신) + 하니스(`dashboard-launch-validate.ps1`).
