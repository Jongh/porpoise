# tide 회고 (retro)

> 누적 마일스톤·보고서를 가로질러 본 회고. 회고 시점마다 이 문서 **최상단에** 새 섹션을
> 쌓는다(기존 섹션 보존). `/tide:retro`가 생성·갱신하는 읽기 전용 산출물.

## 2026-06-11 (v0.35.0 시점)

### 집계 범위

tide `docs/` 체계의 마일스톤 **M37~M38**(2개), impl 보고서 2 + review 보고서 2, 릴리즈
**v0.34.0~v0.35.0**. 두 사이클뿐이라 추세 신뢰도는 제한적이나, M37(런처 출시)→M38(런처 마감)이
명확한 페어라 "출시→잔여 품질 마감"의 한 묶음으로 읽을 가치가 있다.
(porpoise 네이티브 `.porpoise/milestones/` M1~M36은 gitignore·tide 체계 밖이라 회고 입력에서 제외.)

### 반복된 문제·이슈 군집

- **동시성·런 락 정확성** (등장: M37, M38) — 런 락이 두 사이클 연속으로 다듬어졌다. M37: 가드
  확인 후 spawn·이후 락 기록의 **TOCTOU 경쟁**(동시 요청 이중 spawn) → 리뷰 중 락을 spawn 전
  선점으로 **수정**. M38: 시간 기반(30초) 만료가 짧은 런 직후 재실행을 막던 **quirk** → **PID
  생존 기반**으로 **수정**. 추이: 둘 다 수정. 교훈 — 동시성 가정은 라이브/실사용에서 드러난다.
- **detach·spawn 성공 경로가 자동 테스트 밖** (등장: M37, M38) — 실제 spawn은 conductor 런·claude를
  띄워 no-claude HTTP 하니스로 못 덮는다. M37: 라이브 `.ps1`로 **Windows 실측**(gate 블록 → 비용
  0 → 대시보드 종료 후 생존). M38: `.sh`로 **Unix 이식**(작성·미실측). 추이: 라이브 하니스로 점진
  해소, **Unix 실측은 이월**.
- **무결합(파일 매개) 경계 유지 부담** (등장: M37, M38) — 두 사이클 모두 "무결합 원칙 유지선"이
  설계 제약으로 등장. M37: 제어 쓰기를 control/ 한정 → 설정(config)으로 **의도적 확장**(화이트리스트로
  제한). M38: run.lock을 conductor가 모르게 **launcher-side PID 판정**으로 유지. 추이: 원칙 유지하며
  **수용**(범위를 명시적으로 한정).

### 수용된 트레이드오프

- **run.lock 30초 시간 기반 만료** (출처: M37-review 권장3) — 자가 만료로 단순화, sub-30s 차단
  quirk 수용 → **M38에서 PID 기반으로 해소**.
- **toml round-trip 주석 손실** (출처: M37-impl 후속3) — 데이터는 보존, 주석은 손실 수용 →
  **M38에서 toml_edit로 해소**.
- **실행 중 함대 핫-재큐 미지원** (출처: M37-impl 후속4) — 재투입은 "다음 실행에서 효력". 스케줄러
  복잡도 회피 — M38도 범위 밖 유지(2스텝→단일 버튼으로 UX만 개선).
- **PID 재사용 시 과차단** (출처: M38-review 권장2) — 죽은 PID 재사용 시 과차단 가능하나 희박·보수적
  (force로 우회). 수용.
- **`pid_alive` shell-out 비용 / `lock_blocks` 부수효과** (출처: M38-review 사소·권장1) — 빈도 낮아
  shell-out 1회 수용, 판정 함수의 죽은 락 삭제는 주석으로 명시하고 수용.
- **포트 공존을 코드 강제 대신 문서/권장으로** (출처: M38-impl 후속2) — 독립 대시보드 포트와 자식
  `dashboard_port` 불일치 시 두 번째 대시보드 — `serve_dashboard=false` 권장으로 처리.

### 회고 메모

1. **미반영 후속 우선순위**: ① **Unix detach 실측**(`.sh`가 준비됐으니 운영자 Unix 1회 실행이면 닫힘 — 가장 저비용)
   ② **B 묶음(지휘 지능)** — 런처가 완성됐으니 "외부 루프 지능화"가 자연스러운 다음 큰 방향.
   특히 **적응형 재계획(B1)** 은 누적 이월된 **핫-재큐**와 묶으면 시너지(재투입이 "예산만 늘리는" 현재
   한계를 "계획을 고치는" 단계로). ③ `lock_blocks` 분리·`pid_alive` 캐시는 소규모 정리로 끼워넣기.
2. **패턴 — 라이브 검증이 다음 사이클의 후속을 낳는다**: M37 detach 실측 세팅이 M38의 `.sh` 이식과
   PID 락 정밀화로 이어졌다. 라이브 검증을 "릴리즈 게이트"이자 "다음 마일스톤 입력"으로 쓰는 루프가
   효과적. 단, **테스트 불가 영역(실 spawn·OS detach)** 은 자동화 밖이라 운영자 실측 의존이 누적된다 —
   이월 추적(이 표)을 계속 유지할 것.
3. **락·동시성은 초기 설계에서 PID/생존 기반을 우선 고려**: 시간 기반(M37)→PID 기반(M38)의 2단계
   재작업은, 동시성 가정을 처음부터 실사용 시나리오로 검증했으면 1회로 끝났을 여지가 있다.
